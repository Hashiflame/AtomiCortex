## 2. Протокол аудита (действует во всех проходах)

### Железные правила
- **READ-ONLY** по `src/`, `scripts/`, `tests/`, `deploy/`, `config`. Ни одной правки.
  Единственное место записи — `docs/audit2/`.
- **GIT**: только `status` / `diff` / `log`. Никаких операций записи.
- **SUDO**: ни одной команды. На VM НЕ ходить. `/mnt/hdd` не трогать.
- Бота, watchdog, боевые скрипты НЕ запускать.
- Измерения разрешены, артефакты только в `/tmp`. Тяжёлые прогоны (обучение,
  сборка фич) — только если явно разрешены в задании прохода.
- `pytest` — только если явно предписан проходом.
- Только свежий литеральный вывод реально выполненных команд.
  **Реконструкция по памяти ЗАПРЕЩЕНА.**
- Литералы цитировать ДОСЛОВНО. Не удаётся точно воспроизвести — не вставлять
  фрагмент вовсе. Не вставлять строк, которых нет в выводе команды.
- Файла/строки нет → «отсутствует», не додумывать.

### Порядок работы — запись раньше отчёта
Контекстное окно кончится раньше, чем аудит. Поэтому:
1. Исследовать предмет прохода.
2. **ПОЛНОСТЬЮ записать файл** в `docs/audit2/`.
3. Только потом отчитаться в чат — кратко, со ссылкой на файл.

При приближении к пределу контекста: немедленно дописать файл тем, что есть,
пометить незакрытые вопросы разделом «НЕ ИССЛЕДОВАНО», отчитаться.
Потеря наработанного хуже неполноты.

### Формат находки (обязателен)

```
### A2-NN <короткое имя>
**Севирити:** CRITICAL / HIGH / MEDIUM / LOW
**Тип:** логика / семантика / математика / архитектура / мёртвый код /
         недоделка / расхождение с практикой
**Где:** путь:строка (номера — из свежего вывода, не из памяти)
**Что в коде:** дословная цитата, минимально достаточная
**В чём дефект:** почему это неверно
**Как проявляется:** конкретное последствие для чисел или поведения
**Кто ещё это читает:** список потребителей значения/контракта; держится ли
  контракт сквозь них
**Как установлено:** «замером» (команда + вывод) или «чтением»
**Уверенность:** доказано / вероятно / гипотеза
```

### Стандарт доказательства
- «Замером» сильнее «чтением». Где можно измерить — измеряй.
- Гипотезу помечать гипотезой. Не выдавать рассуждение за факт.
- Находка противоречит наблюдаемому поведению системы → наблюдение сильнее,
  перепроверить себя.
- Отличать ДЕФЕКТ от вкусовщины. «Не нравится имя переменной» — не находка.
  «Значение читается двумя модулями в разных единицах» — находка.

### Сквозная линза (применять в каждом проходе)
Для каждого значения, контракта, единицы измерения:
**кто это пишет, кто читает, совпадают ли их допущения?**
Самый опасный класс — модули, корректные по отдельности, но ломающие логику
или математику в связке: разные единицы, разные конвенции времени, разные
определения одного термина, молчаливая деградация одного к дефолту, который
другой считает данными.

### Чего не делать
- Не писать планов исправления, не предлагать код, не рефакторить.
- Не переоткрывать A1…A20 из Аудита-1 как новые находки. Если A-находка жива —
  ссылаться на её номер и показывать, что она не закрыта.
- Не оценивать стиль, форматирование, длину функций.

## 3. Контекст проекта (вход, НЕ перепроверять)

Velontir/AtomiCortex — автоматизированная торговая система на криптоперпетуалах.
LightGBM бинарная классификация по режимам (trend / high_vol / range),
4H BTCUSDT/ETHUSDT/SOLUSDT, режим paper `--dry-run`.
Владелец — единственный разработчик.

Установленные факты:
- валидированной модели нет; прод-бандл — не тот артефакт, для которого
  считались метрики;
- walk-forward AUC 0.5375 (p=0.163), ESS ≈1053 против номинальных 3178;
- live confidence 0.50–0.54 против порога 0.65, сигналов нет;
- данные 2024-01-01 … 2026-08-20, `ml_features` 5038 строк × 3 символа;
- Аудит-1 (2026-07-02) нашёл A1…A20; переоткрывать не надо, но проверить
  фактическую закрытость — надо.

**Цель Аудита-2:** найти дефекты, делающие выводы системы неверными —
логические, семантические, математические, архитектурные. Отдельно — мёртвый
код, недоделки, дубли. Отдельно — расхождение с практикой индустрии.
