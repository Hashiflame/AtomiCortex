### 1.2 По каким ценам срабатывают барьеры — ФАКТ

**Только по `close`.** Дословно, `src/features/triple_barrier.py:124-127`:

```
    for k in range(1, max_holding_bars + 1):
        fut = close[k:k + valid_n]
        up = (~hit) & (fut >= upper)
        dn = (~hit) & (~up) & (fut <= lower)
```

`high` и `low` в файле не встречаются вообще:

```
$ grep -n 'high\|low' src/features/triple_barrier.py
   (только 'max_holding' / 'holding' — совпадений по 'high'/'low' как имён колонок нет)
```

Колонки `high` и `low` в `ml_features` присутствуют (замер схемы:
`['open_time', 'high', 'low', 'close', 'datetime', 'symbol', 'regime',
'atr_pct', 'atr_percentile']`), то есть данные есть — они не используются.

**Исполнение при этом интрабарное.** Стоп и тейк выставляются как цены
(`src/risk/risk_engine.py:276`, `:298`) и срабатывают на бирже по касанию, а
не по закрытию бара. Замер по восьми реальным сделкам (§6.3) это подтверждает:
`close_price` во всех восьми строках **точно равна** `take_profit` или
`stop_loss`, то есть выход произошёл по касанию уровня внутри бара.

**A11 подтверждена: расхождение есть.** См. A2-018.

### 1.3 Оба барьера за один бар

Кода разрешения нет, потому что при сравнении по `close` ситуация невозможна.
Комментарий `triple_barrier.py:120-123` это и утверждает:

```
    # Sweep the holding horizon k = 1 .. max_holding_bars. The first
    # bar that breaches a barrier wins (``~hit`` mask freezes earlier
    # touches). upper is checked before lower; they cannot both trigger
    # on one bar since lower < entry < upper.
```

Утверждение **верно** — одно число `close[t+k]` не может быть одновременно
`>= upper` и `<= lower`. Формальное предпочтение верхнего барьера
(`dn = (~hit) & (~up) & ...`, строка 127) поэтому никогда не применяется.

**Но именно эта невозможность и есть следствие дефекта.** При проверке по
`high`/`low` бар с `high >= upper` и `low <= lower` — обычное явление на
волатильном 4H-баре, и тогда порядок разрешения становится содержательным
выбором (AFML разрешает его через путь внутри бара или консервативно в пользу
стопа). Здесь выбор не сделан, а устранён отказом от интрабарной информации.
Это не «обосновано» — это обойдено.

### 1.5 Включается ли бар входа в окно проверки — off-by-one

**Не включается. Off-by-one отсутствует.**

`triple_barrier.py:124`: `for k in range(1, max_holding_bars + 1)` — `k`
начинается с 1, то есть первый проверяемый бар это `t+1`. `entry = close[t]`
берётся с того же бара `t` (строка 108). Окно — `close[t+1 .. t+h]`,
ровно `h` баров. Это корректно и совпадает с докстрингом (`:65`):

```
      - scan ``close[t+1 .. t+max_holding_bars]``; first barrier touched
```

Замер, подтверждающий: `t1_bar − индекс_входа` для не коснувшихся строк равен
ровно `h` (M3, колонка «сред.k всего» ≤ h, «медиана k|касание» ≥ 1), а
минимальное наблюдённое `k` = 1 (M6b, id=3: `k метки = 1`).

**Хвост.** `df.head(valid_n)` (строка 166) отбрасывает последние `h` строк.
Замер: исходно 5038 строк, после разметки при `h=6` — **5032**, при `h=4` —
**5034** (M1). Ровно `5038 − h`. Корректно.

## 2. ЕДИНИЦЫ И МАСШТАБ БАРЬЕРОВ

### 2.1 Множители чего именно

База — `atr_pct`, **безразмерная** величина ATR/цена. Дословно из сигнатуры
(`triple_barrier.py:52-57`):

```
    close_col: str = "close",
    atr_col: str = "atr_pct",        # ATR / price (dimensionless)
    pt_multiplier: float = 1.5,       # profit-taking barrier = 1.5 × ATR
    sl_multiplier: float = 1.0,       # stop-loss barrier   = 1.0 × ATR
    max_holding_bars: int = 6,        # vertical barrier (bars)
    min_atr: float = 0.001,           # atr_pct floor (1 bp) — div-zero guard
```

и из формулы (`:110-111`):

```
    upper = entry * (1.0 + pt_multiplier * atr_v)
    lower = entry * (1.0 - sl_multiplier * atr_v)
```

Замер значения `atr_pct` в данных: первые строки BTCUSDT дают
`0.020628`, `0.022198`, `0.021277` — то есть **доля**, ≈2.1%, не проценты.
Размерность формулы сходится: `entry × pt × atr_pct` = `pt × ATR` в долларах.

**Замечание о `min_atr`.** Комментарий называет `0.001` «1 bp». Это неверно:
0.001 в долях — это **10 bp**, или 0.1%. Расхождение комментария и значения; на
4H-данных пол не достигается (минимальный наблюдённый `atr_pct` заведомо выше),
поэтому на числа не влияет. Зафиксировано, находкой не оформляется.

### 2.2 Какой ATR

Разметка берёт `atr_pct` **того же бара `t`**, что и `entry = close[t]`
(строки 108–109: `entry = close[:valid_n]`, `atr_v = atr[:valid_n]` — один и тот
же срез). Текущий бар включён. Это причинно корректно: `atr_pct[t]` вычислен по
барам `≤ t`.

Период и способ расчёта задаются в `src/features/` и относятся к проходу 3
(см. «НЕ ИССЛЕДОВАНО»). Для настоящего прохода существенно лишь то, что
`atr_pct` в `ml_features` — единственная база барьеров и что она безразмерна.

### 2.3 Совпадает ли база с базой `risk_engine`

**База — та же, множители — разные.**

`risk_engine` работает с **абсолютным** ATR в долларах
(`src/risk/risk_engine.py:75-76`):

```
    atr: float              # current ATR in $
    atr_pct: float          # ATR / price
```

Стоп (`risk_engine.py:276`):

```
        offset = atr * self._config.atr_stop_multiplier
```
при `atr_stop_multiplier: float = 1.5` (`risk_engine.py:37`).

Тейк (`risk_engine.py:281-299`) — не от ATR напрямую, а от риска:

```
    def calculate_take_profit(
        self,
        entry_price: float,
        direction: int,
        stop_loss: float,
        rr_ratio: float = 1.5,
    ) -> float:
```
```
        risk = abs(entry_price - stop_loss)
        reward = risk * rr_ratio
```

то есть TP = 1.5 × 1.5 × ATR = **2.25 × ATR**.

**Замер на восьми реальных сделках** (M6c) — обе величины подтверждены точно:

```
  SL расстояние / atr: [1.5, 1.5, 1.5, 1.5, 1.5, 1.5, 1.5, 1.5]
  TP расстояние / atr: [2.25, 2.25, 2.25, 2.25, 2.25, 2.25, 2.25, 2.25]
```

**Сопоставление баз:**

| | верхний барьер | нижний барьер | R:R |
|---|---|---|---|
| Разметка, прод-конфиг из `docs/audit/00_index.md:63` (pt=1.0, sl=0.8) | +1.00 × ATR | −0.80 × ATR | 1.25 |
| Разметка, `BEST_CELLS['trend']` в коде (pt=1.25, sl=1.0) | +1.25 × ATR | −1.00 × ATR | 1.25 |
| Разметка, дефолт функции (pt=1.5, sl=1.0) | +1.50 × ATR | −1.00 × ATR | 1.50 |
| **Исполнение** (`risk_engine`) | **+2.25 × ATR** | **−1.50 × ATR** | **1.50** |

База одна (ATR), масштаб — нет. Верхний барьер исполнения **в 2.25 раза**
дальше верхнего барьера разметки в прод-конфиге; нижний — в 1.875 раза.

### 2.4 Проверка размерности

**Размерной ошибки нет.** Разметка масштабирует относительную величину
(`entry × pt × atr_pct`), исполнение — абсолютную (`atr × 1.5`); обе дают
расстояние в долларах, равное `множитель × ATR`. CRITICAL по размерности,
которого требовало задание §2.4, **не подтверждается**.

Дефект лежит не в размерности, а в величине множителей и в способе касания —
см. A2-015 и A2-018.

### A2-021 `p(UP)` меньше 0.5 во всех режимах, включая `trend_up`

**Севирити:** MEDIUM
**Тип:** математика / семантика
**Где:** `src/features/triple_barrier.py:110-111`; замер M1, M2

**Что в коде:**

```
    upper = entry * (1.0 + pt_multiplier * atr_v)
    lower = entry * (1.0 - sl_multiplier * atr_v)
```

**В чём дефект:** при `sl < pt` нижний барьер ближе, поэтому касается чаще —
чисто механически, вне зависимости от прогнозируемости. Замер показывает, что
это доминирует над фактическим дрейфом: **во всех 4 ячейках × 3 символах ×
4 режимах — 48 срезов — `p(UP|бинарно)` ни разу не превышает 0.5.**

Крайний случай: в режиме `trend_up` при прод-конфиге pt=1.0/sl=0.8
`p(UP) = 0.4706`, при pt=1.5/sl=1.0 — `0.4152`. **В восходящем тренде метка
чаще говорит «вниз».**

**Как проявляется:** «событие», которое учится предсказывать модель,
семантически не равно «направление движения». Это «что произошло раньше:
маленькое падение или чуть большее подрастание» — величина, определяемая
геометрией барьеров не меньше, чем рынком. Дальше `compute_sample_weight
("balanced", ...)` (`lgbm_trainer.py:702`) выравнивает классы, то есть
искусственное преобладание `-1` перекладывается в веса, а не устраняется.

**Кто ещё это читает:** `LGBMTrainer._prepare` (бинаризация `-1 → 0`),
`compute_sample_weight` (`lgbm_trainer.py:702-703`), пороги
`confidence_threshold` в стратегиях (0.55 для 4H, `ml_strategy.py:1755-1766`).
Порог сравнивается с `p(class=1)` модели, обученной на выборке с априором
0.42–0.47 — интерпретация «0.65 = высокая уверенность» опирается на
несуществующий симметричный априор.

**Как установлено:** замером (M1, M2).
**Уверенность:** доказано.

### 3.3 Нестационарность априора и её учёт

**Учёта нет.** Единственный механизм — `compute_sample_weight("balanced", ...)`
(`src/models/lgbm_trainer.py:701-703`):

```

        train_weights = compute_sample_weight("balanced", y_train_fit)
        val_weights = compute_sample_weight("balanced", y_val)
```

Что это делает и чего не делает:

- **Делает:** выравнивает классы **внутри** `y_train_fit` и **внутри** `y_val`
  по фактическому априору соответствующего среза.

  считаются раздельно, поэтому модель обучена на априоре train-среза, а
  применяется к периоду с другим априором. Никакой явной коррекции сдвига
  (prior shift correction) нет.

### A2-016 Нормировка `u / u_mean` стирает поправку на эффективный размер выборки

**Севирити:** HIGH
**Тип:** математика
**Где:** `src/models/dataset_builder.py:391-395`; `src/models/lgbm_trainer.py:705-712`

**Что в коде.** `src/models/dataset_builder.py:391-395`:

```
        # Normalize: mean weight = 1 so balanced class weights still mean
        # what they say when multiplied in.
        u_mean = u.mean()
        if u_mean > 0:
            u = u / u_mean
        return u.astype(np.float64)
```

Намерение объявлено дважды. Докстринг `dataset_builder.py:318-320`:

```
        Weights are normalized so the mean weight = 1 — this preserves
        LightGBM's effective sample count and keeps the balanced-class
        weight multiplier interpretable.
```

и комментарий в тренере, `lgbm_trainer.py:705-709`:

```
        # v3: multiply in AFML uniqueness weights (per-symbol concurrency
        # over the triple-barrier holding window). Aligned to train_df row
        # order, so the same val_split slice applies. Multiplied with
        # balanced weights; mean(uniqueness) ≈ 1 so the balanced scale is
        # preserved and LightGBM's effective sample count stays in range.
```

**В чём дефект:** «preserves LightGBM's effective sample count» и «effective
sample count stays in range» — это и есть отменённая поправка. Смысл весов
уникальности по AFML Ch.4 в том, что при перекрывающихся метках эффективный
размер выборки **меньше** номинального, и `sum(w)` должна это отражать.
Нормировка на среднее делает `sum(w) = n` тождественно.

**Замер — прямое подтверждение** (M5, две последние группы колонок):

| Символ (pt=1.0/sl=0.8/h=6) | n | `sum(u)` до нормировки | `sum(w)` после |
|---|---|---|---|
| BTCUSDT | 3482 | **1048.8** | **3482.0** |
| ETHUSDT | 3365 | **1011.0** | **3365.0** |
| SOLUSDT | 3700 | **1091.9** | **3700.0** |

Отношение `ESS/n` = 0.295…0.305. То есть в данных примерно **30%** независимой
информации от номинального объёма, и нормировка возвращает счётчик к 100%.
`mean(w) = 1.0000` во всех девяти строках замера.

Что **сохраняется**: относительные веса внутри символа — метки с ранним выходом
по PT/SL получают больший вес. Что **теряется**: абсолютный масштаб, то есть
именно тот компонент, из-за которого номинальные 3482 наблюдения нельзя
трактовать как 3482 независимых.

Дополнительно: нормировка выполняется **отдельно для каждого символа**
(`compute_uniqueness_weights_by_symbol`, `dataset_builder.py:425-441` — вызов
`compute_uniqueness_weights` внутри цикла по символам). Поэтому стирается и
относительная разница между символами: SOLUSDT с конкурентностью 3.105 и
ETHUSDT с 2.886 после нормировки вносят одинаковый суммарный вес на строку.

**Как проявляется:** LightGBM видит `sum(weight) = n` и строит деревья, ранние
остановки и оценки расщеплений так, будто наблюдений втрое больше, чем
независимой информации. Все статистики, опирающиеся на объём выборки —
доверительные интервалы, t-статистика, DSR — переоценивают значимость примерно
в `sqrt(1/0.30) ≈ 1.8` раза. Именно это соотношение стоит за входным фактом
«walk-forward AUC 0.5375 (p=0.163)».

**Кто ещё это читает:** `lgbm_trainer.py:710-721` (единственный потребитель
весов), `scripts/retrain_v3.py:182` (см. A2-020). Ни один потребитель не
использует `sum(u)` как оценку ESS — величина вычисляется и уничтожается внутри
одной функции.

**Отношение к бэклогу:** R-2 подтверждён **замером**, а не чтением, как и
требовало задание.

**Отношение к Аудиту-1:** `docs/code_review_v3.md:23` фиксировал смежный, но
**другой** дефект — «`compute_uniqueness_weights` assumes all labels span
exactly `max_holding`». Он **закрыт**: появился режим реального `t1`
(`dataset_builder.py:358-386`), и замер M5 использует именно его. Нормировка
на среднее — отдельный, не закрытый дефект.

**Как установлено:** замером (M5) и чтением.
**Уверенность:** доказано.

### 4.3 Перекрытие против сплита train/test — ПРОВЕРЕНО, ДЕФЕКТА НЕТ

Эмбарго измеряется в **wall-clock времени** и равно ровно горизонту метки.
`src/models/lgbm_trainer.py:522-525`:

```
        embargo_bars = (
            self.config.barrier_max_holding
            if self.config.use_triple_barrier
            else max(1, self.config.forward_bars)
        )
```

и применение, `lgbm_trainer.py:552-554`:

```
            embargo_cutoff = oos_start_ms - embargo_bars * bar_ms
            n_pre_embargo = len(train_df)
            train_df = train_df.filter(pl.col("open_time") < embargo_cutoff)
```

Последний оставшийся train-бар имеет `open_time < oos_start − h × bar_ms`,
значит его метка выходит строго раньше `oos_start`. **Бар теста, чья метка
построена на будущем из train, невозможен.** Тот же горизонт применяется на
границе fit→val (`lgbm_trainer.py:684-689`, `_embargo_fit_end`).

Комментарий `lgbm_trainer.py:516-521` показывает, что переход от строк к
времени сделан осознанно — после `drop_timeout` уцелевшие строки редки, и
эмбарго в строках перекрыл бы сотни баров.

Смежная находка Аудита-1 `docs/audit/04_models_and_training.md:58` («`X_val =
X_train[val_split:]` тянется до конца train-части, чьи последние h=6 лейблов…»)
закрывается тем же механизмом: train-часть уже отсечена от теста на `h` баров,
поэтому хвост val не может смотреть в тест.

**Оговорка.** Эмбарго защищает от утечки *через границу*. Оно не устраняет
перекрытие *внутри* train и *внутри* test — а именно оно порождает
ESS/n ≈ 0.30 (M5). Эти две вещи часто смешивают; здесь первая решена, вторая —
нет (A2-016).

### 5.3 Соответствие `h` характерному времени движения

Замер M3, колонка «сред.k|касание» — среднее число баров до первого касания
среди сработавших:

| Конфиг | среднее `k` при касании | медиана | `h` | отношение сред./`h` |
|---|---|---|---|---|
| pt=1.0, sl=0.8, h=6 | 3.05–3.09 | 3.0 | 6 | 0.51 |
| pt=1.25, sl=1.0, h=4 | 2.49–2.58 | 2.0–3.0 | 4 | 0.63 |
| pt=1.25, sl=1.0, h=6 | 3.27–3.38 | 3.0 | 6 | 0.55 |

Характерное время до касания барьера ≈1.0–1.25 ATR составляет **3 бара 4H = 12
часов**, при горизонте 6 баров = 24 часа. То есть `h` примерно вдвое больше
характерного времени события — вертикальный барьер не «обрезает» типичное
движение, он ловит хвост.

Это **не дефект сам по себе**: горизонт вдвое длиннее медианы — разумный запас.

отношение 0.63, при котором вертикальный барьер начинает конкурировать с
горизонтальными и отсекает больше половины выборки (§5.2).

**Отдельно, и это важнее** — исполнение не имеет вертикального барьера вовсе,
и замер по реальным сделкам показывает выходы на **11-м и 21-м баре** (§6.3),
то есть в 1.8 и 3.5 раза дальше горизонта разметки.

### A2-015 Разметка и исполнение описывают разные события

**Севирити:** CRITICAL
**Тип:** математика / семантика / архитектура
**Где:** `src/features/triple_barrier.py:110-111`, `:125`;
`src/risk/risk_engine.py:37`, `:276`, `:285`, `:298`;
`scripts/retrain_v3.py:70-71`; `docs/audit/00_index.md:63`

**Что в коде.** Разметка (`triple_barrier.py:110-111`, `:125`):

```
    upper = entry * (1.0 + pt_multiplier * atr_v)
    lower = entry * (1.0 - sl_multiplier * atr_v)
```
```
        fut = close[k:k + valid_n]
```

Исполнение (`risk_engine.py:276`, `:296-297`):

```
        offset = atr * self._config.atr_stop_multiplier
```
```
        risk = abs(entry_price - stop_loss)
        reward = risk * rr_ratio
```
при `atr_stop_multiplier: float = 1.5` (`risk_engine.py:37`) и
`rr_ratio: float = 1.5` (`risk_engine.py:286`).

**В чём дефект — четыре независимых расхождения, все в одну сторону:**

1. **Масштаб.** Верхний барьер исполнения (2.25 ATR) в **2.25 раза** дальше
   верхнего барьера разметки в документированном прод-конфиге (1.0 ATR); нижний
   (1.5 ATR) — в **1.875 раза** дальше нижнего (0.8 ATR).
2. **R:R.** Разметка учит на R:R 1.25, торгуется R:R 1.50.
3. **Цена касания.** Метка требует, чтобы **закрытие** бара пробило уровень;
   ордер срабатывает от **любого касания** внутри бара. Для одного и того же
   ценового пути метка и исполнение дают разный исход.
4. **Время.** Метка ограничена `h` барами; позиция — не ограничена ничем.

**Как проявляется — направление смещения.**

Пункты 1 и 2 смещают результат **в худшую сторону**. Событие «цена прошла
1.0 ATR вверх раньше, чем 0.8 ATR вниз» наступает существенно чаще, чем «цена
прошла 2.25 ATR вверх раньше, чем 1.5 ATR вниз»: первое требует движения в
2.25 раза меньшего. `p(UP)` модели откалибрована (точнее — не откалибрована,
§3.3) под первое событие и применяется как оценка вероятности второго.
Уверенность модели поэтому систематически **оптимистична** относительно сделки,
которую она запускает.

Замер, показывающий разрыв величин напрямую (M6b, конфиг pt=1.0/sl=0.8/h=6):
для сделки id=1 метка `−1` с `future_return = −0.93%`, тогда как сделка по
той же точке входа принесла **+2.09%** (шорт). Метка фиксирует движение 0.93%;
исполнению нужно 2.09%. Для id=8 метка `−1`, `future_return = −2.18%`, сделка
шла в LONG и потеряла −2.30% — метка и сделка смотрели в разные стороны.

Пункт 3 смещает **в лучшую сторону для стопа и в худшую для тейка**
одновременно: интрабарное касание срабатывает раньше и по обоим уровням, но
поскольку стоп ближе, чаще выбивает именно он. Чистое направление —
**в худшую**.

Пункт 4 смещает **непредсказуемо, но с ростом дисперсии**: метка ничего не
знает о том, что произойдёт после бара `t+h`, а позиция там остаётся. Замер:
2 из 8 сделок (**25%**) закрылись на 11-м и 21-м баре, то есть за пределами
горизонта разметки (M6c: `длительность в барах 4H: [2, 1, 1, 11, 21, 4, 2, 1]`).

**Кто ещё это читает:** `MLTradingStrategy.on_bar` сравнивает `confidence`
модели с `confidence_threshold` (`ml_strategy.py:1754-1766`) и передаёт сигнал
в `RiskEngine.evaluate`, который строит SL/TP по собственным множителям. Ни
одного места, где два набора множителей сверялись бы между собой, в коде нет:

```
$ grep -rn 'atr_stop_multiplier\|pt_multiplier' src | grep -v 'triple_barrier.py\|risk_engine.py\|dataset_builder.py'
   (пусто)
```

Контракт «что означает выход модели» через границу разметка→исполнение
**не держится** и нигде не проверяется.

**Отношение к Аудиту-1:** A6 («SL 1.5·ATR / TP 2.25·ATR интрабарно, без
time-exit») зафиксирована во входных фактах. **Не закрыта.** Настоящая находка
добавляет к ней замер масштаба расхождения и его направление.

**Как установлено:** замером (M6, §2.3) и чтением.
**Уверенность:** доказано.

### A2-018 Барьеры разметки проверяются только по `close`, при интрабарном исполнении

**Севирити:** HIGH
**Тип:** математика
**Где:** `src/features/triple_barrier.py:125`

**Что в коде:**

```
        fut = close[k:k + valid_n]
```

**В чём дефект:** на 4H-баре диапазон `high − low` регулярно превышает 1 ATR,
поэтому бар, закрывшийся между барьерами, часто **касался** одного из них
внутри. Разметка такой бар считает «ничего не произошло» (или относит к
позднейшему касанию), исполнение — сработавшим. Данные для корректной проверки
в кадре есть: колонки `high` и `low` присутствуют в `ml_features` (замер схемы,
§1.2), но `triple_barrier.py` их не читает.

**Как проявляется:** метка систематически **занижает** частоту касаний и
**завышает** время до касания. Замер §5.3 даёт среднее время до касания 3.05
бара — по `close`. По `high`/`low` оно было бы меньше. Соответственно доля
истечений (26.5–33.1% при h=6) завышена, а доля срабатываний занижена. Модель
учится на событии, которое наступает реже и позже, чем то, что торгуется.

Отдельное следствие — устранённая, а не решённая неоднозначность «оба барьера
за один бар» (§1.3).

**Кто ещё это читает:** `future_return` (`triple_barrier.py:139-140`) тоже
берётся по `close` на баре касания, поэтому P&L валидаторов унаследует то же
смещение.

**Отношение к Аудиту-1:** A11. **Не закрыта.**

**Как установлено:** чтением кода и замером схемы данных (наличие
неиспользуемых `high`/`low`). Прямой замер разницы «касание по close против
касания по high/low» **не проводился** — см. «НЕ ИССЛЕДОВАНО» п.3.
**Уверенность:** доказано для механики; величина смещения — гипотеза.

   ответ, противоположный своей же метке.
2. **id=5 — сделка жила 21 бар при горизонте разметки 6.** Метка при
   pt=1.25/h=4 — истечение (`0`), при pt=1.0/h=6 — `−1` с
   `future_return = −0.92%`. Фактический результат: +2.31% за 21 бар. Метка не
   описывает 15 из 21 баров этой сделки.
3. **id=4 — сделка жила 11 баров, метка — истечение** с
   `future_return = −0.08%`. Фактический результат: −1.57%. Метка сообщает
   «движения нет», исполнение фиксирует убыток на стопе через 11 баров.
4. **Разрыв в масштабе.** Столбцы `fut_ret%` (что зафиксировала метка) и `pnl%`
   (что зафиксировала сделка) отличаются в разы: −0.93% против +2.09% (id=1),
   −1.20% против +1.97% (id=3), −1.07% против +2.11% (id=6). Метка и сделка
   измеряют движения разного размера — количественное подтверждение A2-015.
5. **Смена конфига меняет метку задним числом.** Для id=1 `future_return`
   меняется с −0.93% (pt=1.0/h=6) на −2.98% (pt=1.25/h=4); для id=5 метка
   меняется с `−1` на `0`. «Правильный ответ» для одного и того же бара зависит
   от того, какой из четырёх наборов барьеров выбран (A2-019).

**Итог по восьми сделкам** (M6c):

```
  wins=4 losses=4
  сумма pnl_pct (gross) = 1.6172%   средн = 0.2021%
  длительность в барах 4H: [2, 1, 1, 11, 21, 4, 2, 1]
  close_price == take_profit/stop_loss точно: 8/8
  SL расстояние / atr: [1.5, 1.5, 1.5, 1.5, 1.5, 1.5, 1.5, 1.5]
  TP расстояние / atr: [2.25, 2.25, 2.25, 2.25, 2.25, 2.25, 2.25, 2.25]
```

Win rate 50.0% при R:R 1.5. Сумма **валовая**: `close_price` во всех восьми
строках равна ровно уровню TP или SL — ни проскальзывания, ни комиссии в записи
нет. При `_ROUND_TRIP_COST = 0.0007` восемь круговых сделок стоят 0.56%, что
даёт нетто ≈ +1.06%; при реальных издержках `CostModel` (≥0.09% круг плюс
слиппедж) — заметно меньше. Восьми сделок в любом случае недостаточно для
статистического вывода; они ценны как **сверка механики**, а не как оценка
доходности.

## 7. ПРЯМОЙ ОТВЕТ

> **Предсказывает ли система то событие, которое торгует?**
>
> **НЕТ.**

Модель обучается отвечать на вопрос: «коснётся ли **закрытие** одного из
следующих ≤6 баров уровня **+1.0 ATR** раньше, чем уровня **−0.8 ATR**, —
при условии, что хотя бы один из них будет задет».

Торгуется вопрос: «сработает ли **интрабарно** уровень **+2.25 ATR** раньше
уровня **−1.5 ATR**, **без ограничения по времени**».

Различаются: расстояние барьеров (в 1.9–2.25 раза), соотношение риск/прибыль
(1.25 против 1.50), цена срабатывания (close против high/low), наличие
ограничения по времени (есть против нет), и условие отбора (обучение видит
только бары, где барьер сработал, — 43–69% от всех; торговля применяется ко
всем 100%).

Совпадает только база масштаба — ATR текущего бара.

Из шести измеренных расхождений пять смещают реальный результат **в худшую
сторону** относительно предсказанного, шестое увеличивает дисперсию. Замер по
восьми реальным сделкам показывает разрыв напрямую: метка фиксирует движения
0.9–2.2%, сделки — 1.4–2.3% в противоположных случаях, две из восьми сделок
(25%) прожили дольше горизонта разметки, и в одном случае (id=2) метка и
открытая позиция смотрели в противоположные стороны.

### A2-022 Две прод-модели обучены на разных определениях события

**Севирити:** CRITICAL
**Тип:** математика / семантика
**Где:** `data/features/models/v3/trend_model_v3.pkl` против
`data/features/models/v3/high_vol_model_v3.pkl`;
маршрутизация — `src/execution/strategies/ml_strategy.py:1739-1766`

**Что измерено:** манифесты двух моделей, которые прод-стратегия загружает
по одному и тому же шаблону имени и между которыми переключается по режиму:

| Бандл | `barriers` | обучающих строк |
|---|---|---|
| `trend_model_v3.pkl` | pt=**1.0**, sl=**0.8**, max_holding=**6** | 3223 |
| `high_vol_model_v3.pkl` | pt=**1.25**, sl=**1.0**, max_holding=**4** | 684 |

**В чём дефект:** `trend_model` предсказывает «коснётся ли close уровня
+1.0 ATR раньше −0.8 ATR за ≤6 баров»; `high_vol_model` — «коснётся ли close
уровня +1.25 ATR раньше −1.0 ATR за ≤**4** бара». Это **два разных события**:
разные расстояния, разный горизонт (24 часа против 16), разное R:R (1.25 против
1.25 — совпадает случайно, при разных абсолютных величинах).

Их выходы сравниваются с **одним и тем же порогом**. `_select_model`
(`ml_strategy.py:1755-1760`):

```
        if regime_label in ("trend_up", "trend_down"):
            return self._trend_model, self._trend_features, base_threshold
        if regime_label == "range":
            return self._trend_model, self._trend_features, max(base_threshold, 0.60)
        if regime_label == "high_vol":
            return self._highvol_model, self._highvol_features, base_threshold
```

`base_threshold = self._config.confidence_threshold` — одно число для обеих
моделей. «0.65» для `trend_model` и «0.65» для `high_vol_model` означают
уверенность в наступлении разных событий с разной априорной частотой. Замер M2
(BTCUSDT) даёт для этих двух конфигураций разные априоры: `p(UP)` = 0.4706 в
`trend_up` при pt=1.0/sl=0.8/h=6 против 0.3984 в `high_vol` при
pt=1.25/sl=1.0/h=4. Пороги несопоставимы по построению.

Дополнительно: режим `range` (1237 баров BTCUSDT, 24.6% выборки) обслуживается
`trend_model`, обученной на барах режима `trend` — то есть на другом
распределении, с порогом, поднятым до 0.60 без обоснования в коде.

**Как проявляется:** маршрутизация по режиму, задуманная как «своя модель на
свой рынок», на деле переключает между двумя разными вопросами, отвечая на них
по одной шкале. Ни одного места, где параметры разметки бандла сверялись бы
между собой или с порогом, в коде нет — `_load_models`
(`ml_strategy.py:1716-1737`) читает из бандла только `booster` и
`feature_columns`:

```
                bundle = LGBMTrainer.load_model_bundle(path)
                booster = bundle["booster"]
                features = bundle.get("feature_columns", [])
```

Поле `manifest`, содержащее `barriers`, прод-кодом **не читается**:

```
$ grep -rn "manifest" src/execution/strategies/ml_strategy.py
   (пусто)
```

**Как установлено:** замером (чтение манифестов) и чтением.
**Уверенность:** доказано.

### A2-023 Бандлы на диске записаны кодом, предшествующим двум исправлениям того же дня; в манифестах — пересечение train и test

**Севирити:** HIGH
